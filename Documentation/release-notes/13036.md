### CRC64 API changes

[GitHub PR #13036](https://github.com/dotnet/android/pull/13036), related to
[GitHub Issue #11467](https://github.com/dotnet/android/issues/11467), replaces
the custom CRC64 engine with the parameterized `System.IO.Hashing`
implementation. Generated Java package names and legacy checksum bytes
remain unchanged on supported little-endian targets.

#### Breaking changes

- `Microsoft.Android.Build.Tasks.Crc64` is removed from
  `Microsoft.Android.Build.BaseTasks.dll`. Custom tooling that referenced or
  derived from this type must migrate and rebuild. Previously compiled
  consumers that require the removed type cannot load it from the new
  assembly.
- `Java.Interop.Tools.JavaCallableWrappers.Crc64` is obsolete in its owning
  JavaCallableWrappers assembly and in `Mono.Android.dll`. The type still
  derives from `HashAlgorithm` and retains its existing behavior and member
  signatures. New compilations produce warning CS0618, which can fail builds
  that treat warnings as errors.
- `Java.Interop.Tools.TypeNameMappings.dll` no longer includes its incidental
  copy of the public `Java.Interop.Tools.JavaCallableWrappers.Crc64` type.
  Consumers referencing that copy must migrate rather than rely on the
  same-named type in a different assembly.

`Crc64Helper` remains an internal implementation detail, not a replacement
public API. `Files.HashBytes`, `Files.HashFile` and `Files.HashStream` continue
to use their existing ECMA-182-based hashes; do not switch those callers to
Jones hashing.

#### Choosing a replacement

First decide whether your code needs to preserve the old checksum values.
Using the default **ECMA-182** algorithm in `System.IO.Hashing.Crc64` is the
simpler option when compatibility with legacy values is not required. For
example, custom tooling that only uses CRCs to detect changes can consider
`System.IO.Hashing.Crc64.Hash (input)` or a parameterless instance with
`Append` and `GetCurrentHash`. No custom parameters or additional length XOR
are needed for the library's default algorithm.

Switching to ECMA-182 changes the checksum values. Recompute stored
checksums or invalidate affected caches as appropriate, and do not mix
checksums produced by the two algorithms.

Keep the Jones behavior when matching existing checksums, reproducing
historical Java package names, or interoperating with a format or component
that depends on those values. The .NET for Android naming pipeline retains
that behavior in this change; the recipe below is for migrating custom code
that also requires byte-for-byte compatibility.

#### Preserving legacy Jones checksums

Reference a `System.IO.Hashing` package that exposes `Crc64ParameterSet`, such
as **11.0.0-rc.1.26425.128**. The library is a separate NuGet dependency;
targeting a newer .NET runtime alone does not provide it.

The parameterless `System.IO.Hashing.Crc64` uses **ECMA-182**, not Jones.
To preserve the old output, use the following Jones parameters, XOR the
**total number of input bytes** into the final CRC, and write the result in
**little-endian byte order**. The length XOR is specific to the legacy
Android implementation; specifying Jones parameters alone is insufficient.
Cache the parameter set because its construction precomputes tables and
vectorization constants.

```csharp
using System;
using System.Buffers.Binary;
using System.IO.Hashing;

static class LegacyJonesChecksum
{
	static readonly Crc64ParameterSet jones = Crc64ParameterSet.Create (
		polynomial: 0xad93d23594c935a9UL,
		initialValue: ulong.MaxValue,
		finalXorValue: 0,
		reflectValues: true);

	public static byte [] Compute (ReadOnlySpan<byte> input)
	{
		ulong crc = System.IO.Hashing.Crc64.HashToUInt64 (jones, input);
		return Finish (crc, (ulong) input.Length);
	}

	public static byte [] ComputeChunks (ReadOnlyMemory<byte> [] chunks)
	{
		var crc = new System.IO.Hashing.Crc64 (jones);
		ulong length = 0;
		foreach (var chunk in chunks) {
			crc.Append (chunk.Span);
			length += (ulong) chunk.Length;
		}
		return Finish (crc.GetCurrentHashAsUInt64 (), length);
	}

	static byte [] Finish (ulong crc, ulong length)
	{
		byte [] hash = new byte [8];
		BinaryPrimitives.WriteUInt64LittleEndian (hash, crc ^ length);
		return hash;
	}
}
```

For incremental or stream input, call `Append` for each chunk and track its
byte count. Apply the length XOR only when reading the result, not between
chunks. If the hasher is reused, call `Reset` and reset the byte count to zero.
Use the number of bytes actually appended, including when hashing an array
slice or reading a stream from its current position.

`System.IO.Hashing.Crc64` is not a `HashAlgorithm`. Code that requires that
base type must provide its own adapter retaining the final length XOR rather
than directly substituting the library type. As a compatibility example,
UTF-8 bytes for `"hello"` produce `AD3D04BD697EB3C5` with the recipe above.
