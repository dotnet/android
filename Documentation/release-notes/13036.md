### CRC64 API changes

[GitHub PR #13036](https://github.com/dotnet/android/pull/13036), related to
[GitHub Issue #11467](https://github.com/dotnet/android/issues/11467), replaces
the custom CRC64 engine with `System.IO.Hashing`. Generated Java package
names and legacy checksum bytes remain unchanged.

#### Breaking changes

- `Microsoft.Android.Build.Tasks.Crc64` is removed from
  `Microsoft.Android.Build.BaseTasks.dll`; consumers must migrate and rebuild.
- `Java.Interop.Tools.JavaCallableWrappers.Crc64` is obsolete in its owning
  assembly and in `Mono.Android.dll`, producing CS0618. Its behavior and
  signatures remain unchanged.
- `Java.Interop.Tools.TypeNameMappings.dll` no longer includes its copy of
  that public type.

#### Migration

Consider the default **ECMA-182** algorithm in `System.IO.Hashing.Crc64`
when historical checksum compatibility is unnecessary. Use `Crc64.Hash (input)`
without custom parameters or a length XOR. Switching algorithms changes
checksum values, so recompute stored checksums or invalidate affected caches.

Only retain Jones behavior when existing hashes or Java package names must
match. With a package exposing `Crc64ParameterSet` (such as
**11.0.0-rc.1.26425.128**):

1. Cache `Crc64ParameterSet.Create` with `polynomial: 0xad93d23594c935a9UL`,
   `initialValue: ulong.MaxValue`, `finalXorValue: 0`, `reflectValues: true`.
2. XOR `Crc64.HashToUInt64 (parameters, input)` with `(ulong) input.Length`.
   For incremental input, use `new Crc64 (parameters)` and `Append`, then XOR
   `GetCurrentHashAsUInt64 ()` with the total byte count only at finalization.
   Reset that count whenever resetting the hasher.
3. Serialize the result with `BinaryPrimitives.WriteUInt64LittleEndian`.

These APIs belong to `System.IO.Hashing`, not the obsolete wrapper. The
library type is not a `HashAlgorithm`; callers requiring that base type
need an adapter. `Crc64Helper` is internal, not a replacement public API.
