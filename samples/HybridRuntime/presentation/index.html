Implementation concept 1

NativeAOT owns startup and schedules warmup after focus.

Shell/MainActivity.cs

protected override void OnCreate (Bundle? state)
{
    base.OnCreate (state);

    if (GetPreferences ().GetBoolean (
        "authenticated", false)) {
        ShowLanding ();
    } else {
        ShowLogin ();
    }
}

public override void OnWindowFocusChanged (bool hasFocus)
{
    base.OnWindowFocusChanged (hasFocus);
    if (!hasFocus || coreClrWarmupRequested)
        return;

    coreClrWarmupRequested = true;
    Window?.DecorView.Post (() =>
        SendBroadcast (CreateExplicitIntent (
            "net.dot.hybrid.CoreClrWarmupReceiver")));
}

Why after window focus?

The shell gets first claim on CPU, linker activity, UI inflation, and first frame delivery. CoreCLR work begins only once useful pixels have won the race.

Why a receiver and bound service?

The receiver bridges NativeAOT to Java, then holds a cross-process service binding. Android keeps the warmed process important and automatically reconnects it after a crash.

Why persist auth in the shell?

Returning users bypass login before the heavy runtime exists. Android SharedPreferences provides the smallest durable decision point.

public static void PrepareForNavigation ()
{
    foreach (Type pageType in PageTypes) {
        foreach (MethodInfo method in
            pageType.GetMethods (
                BindingFlags.DeclaredOnly |
                BindingFlags.Instance |
                BindingFlags.Static |
                BindingFlags.Public |
                BindingFlags.NonPublic)) {
            RuntimeHelpers.PrepareMethod (
                method.MethodHandle);
        }
    }
}

The overlap matters

Process isolation is observable—and survives failure.

2 PIDs

Disjoint runtime DSOs

The shell maps only libHybridRuntimeShell.so; :coreclr maps CoreCLR, JIT, host, and assembly-store libraries.

3 signals

Independent handlers

The SigCgt masks differ for SIGINT, SIGQUIT, and SIGTERM. Handler installation is process-local.

298 ms

Crash and rebind

After killing only CoreCLR, the NativeAOT UI stayed responsive and Android rebound a fresh CoreCLR process.

The runtimes share an APK and Android task—not a signal table, address space, GC heap, or crash fate.
Median CoreCLR initialization and 100-page preparation was ~387 ms after service creation. The current prototype opens a CoreCLR-process Activity; rendering a production MAUI navigation surface is the next decisive experiment.

Engineering risks

Isolation resolves runtime collisions—but creates a distributed app.

  • IPC and state transfer. Authentication, navigation arguments, session state, and readiness cross a process boundary.
  • Lifecycle coordination. Android may reclaim or restart the CoreCLR process independently; every request needs disconnect and retry behavior.
  • Activity integration. Back stack, results, transitions, themes, accessibility, and deep links must still feel like one app.
  • Diagnostics. Logs, traces, crash reports, and health signals must correlate two PIDs into one user journey.
  • Memory doubles quickly. Two GC heaps, two runtime infrastructures, JIT code, and duplicated framework assets trade memory for latency.
  • Package size. The prototype APK is 47.91 MiB because it mechanically combines runtime payloads without product-level deduplication.
  • UI handoff. Navigation, back stack, themes, accessibility, state, and transitions must look like one app across ownership.
  • Unsupported assumptions. Runtime hosts were designed around one selected runtime; this path needs explicit contracts and tests.

Resolved by construction: NativeAOT and CoreCLR no longer compete for process-global signal handlers, exception machinery, native symbols, or address-space assumptions.

What is proven vs. what remains

The runtime hypothesis works. The product boundary is next.

Proven in the prototype

  • One signed APK contains NativeAOT and CoreCLR payloads
  • Each runtime occupies an independent PID with disjoint runtime libraries and signal handlers
  • A bound service initializes CoreCLR asynchronously after first focus
  • CoreCLR invokes managed application code and prepares 100 XAML pages
  • NativeAOT remains responsive while CoreCLR is killed, rebound, and reinitialized
  • Authentication persists and returning users skip login

Required for a product direction

  1. Launch and display a CoreCLR-owned MAUI page from the NativeAOT shell
  2. Implement seamless navigation, back stack, state transfer, and failure UX
  3. Define IPC contracts, readiness, state transfer, disconnect, retry, and degraded-mode behavior
  4. Create first-class dual-runtime build and packaging support
  5. Deduplicate framework/runtime assets and establish size/memory budgets
  6. Benchmark physical devices across cold install, warm cache, and representative app workloads

Conclusion

Treat the runtime as a progressively loaded capability, not a prerequisite for the first pixel.

The prototype demonstrates a credible path: NativeAOT handles the latency-sensitive edge, CoreCLR warms behind it, and a large MAUI payload becomes callable before the user needs it.

Optimize perception

Prioritize useful UI and interaction over completion of the entire application graph.

Make readiness explicit

Model heavy runtime initialization as an observable state with success, failure, retry, and fallback behavior.

Prove the handoff

The next milestone is a production-shaped transition into a CoreCLR-owned MAUI screen.
